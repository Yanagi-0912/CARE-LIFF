狀態：待後端實作
提出方：LIFF 前端
對應產品設計：`2026-09-11-appointment-lifecycle-design.md`

## 這份文件是什麼

掛號提醒上線後發現一個問題：**一筆掛號建立之後沒有出口。** 醫院改期或不去了，使用者唯一能做的是刪除，紀錄整筆消失；過去的紀錄會無上限地累積，而清單 API 沒有分頁，每次打開頁面都把全部歷史撈回來。

產品已經拍板了一套生命週期（取消、未到診後續、清理），這份文件列出前端需要後端補的三件事，外加一條上次追加、可能還沒實作的規則。

前端已經先做完不需要等後端的部分（過去的紀錄可以單筆刪除，走既有的 `DELETE /reminders/{id}`）。

## 已拍板的產品決策（照做即可，不需要再問）

- **取消與刪除是兩件事。**「取消這次門診」保留紀錄、停止推播；「刪除這筆紀錄」才是整筆消失。
- **取消不發任何推播。** 本人取消不通知家屬，家屬代為取消也不另外通知本人。取消本來就會讓後續推播全部停止，家屬自然會發現。
- **掛號紀錄永久保留，不做任何自動刪除或保留期排程。** 清除資料由使用者自己按「刪除這筆紀錄」或「刪除全部歷史紀錄」。
- **不做「補登到診」。** `attend` 維持現有「門診當天才能回報」的限制，不要放寬。
- **只有讀取權的家人（MEMBER）不能更動掛號，影子模式下也一樣。** 所有掛號寫入路徑改成嚴格判定，家屬推播也只送 GUARDIAN、CAREGIVER（見需求五）。
- **「刪除全部歷史紀錄」只有本人可以按。** 家屬一律不行，GUARDIAN、CAREGIVER、受委任者都一樣（見需求五）。

## 需求一：取消這次門診

### `POST /api/appointments/reminders/{reminder_id}/cancel`

- **權限**：與 `depart`／`attend` 相同——本人，或對就診者有 `GENERAL WRITE` 的家屬。沿用同一個授權檢查，並且用嚴格判定（`has_legacy_equivalent=False`，見需求五）：只有讀取權的 MEMBER 不能取消。
- **不需要 body**（帶了也忽略），與 `depart`／`attend` 一致。
- **狀態轉移**：

  | 目前狀態 | 結果 |
  |---|---|
  | `scheduled`、`departed` | 200，轉為 `cancelled` |
  | `cancelled` | **200 冪等**，內容逐字相同，保留第一位取消者（與 depart／attend 重複按的處理一致） |
  | `attended` | 409 |
  | `missed` | 409 |

- **寫入**：`cancelled_at`、`cancelled_by_user_id`，慣例與 `departed_at`／`departed_by_user_id` 相同（`cancelled_at` 帶 `appointment_at` 的 offset 輸出）。
- **推播**：取消所有尚未發出的推播，本人與家屬都一樣（T-1h、T+0、T+30）。回應的 `notify_at` 應為空陣列。
- **不發任何「已取消」通知**（已拍板）。
- **不限門診當天**：跟 depart／attend 不同，取消通常發生在門診前幾天。

### 已經送出的 LINE 卡片

取消之後，使用者手機上可能還留著先前收到的 T-1h 卡片，上面的「我已出發」「我已到診」仍按得下去。後端報告 §9 已有這個情況的處理（回一則純文字「這筆掛號提醒已經取消，無法回報出發或到診。」），請確認這條路徑在 `cancelled` 真的會被寫入之後依然正確。

### 已取消的掛號不能再改門診時間（變更既有行為）

後端報告 §2.7／§3.2 寫到「改門診時間：`scheduled`／`departed`／`missed`／`cancelled` → `scheduled`」，也就是 `PUT` 改 `appointment_at` 會把已取消的掛號復活。

請改成：**已取消的掛號 `PUT` 改 `appointment_at` 回 409**，與已到診的處理一致。

理由：產品上 `cancelled` 是終局。改期的正確做法是「再掛一次」新增一筆，舊的那筆留著當作「這次門診後來取消了」的紀錄；直接改時間會把歷史改寫掉，使用者回頭查時會以為那次門診從來沒有取消過。前端不會對已取消的掛號提供改時間的入口，這條是後端的防線。

`missed` 維持現狀（可以改時間重置回 `scheduled`）——那個情境是「時間填錯了所以沒去成」，前端目前也不會開放，維持即可，不需要動。

### 錯誤 detail（繁中，建議文案，可調整）

| 狀態 | detail |
|---|---|
| 403 | 您沒有權限替這位家人取消門診。 |
| 404 | 找不到這筆掛號提醒，可能已經被刪除。（沿用既有） |
| 409（已到診） | 已經回報到診的門診不能取消。 |
| 409（未到診） | 這個門診的當天已經結束，不需要取消。 |
| 409（PUT 改已取消掛號的時間） | 已經取消的掛號不能改時間；如果要改期，請新增一筆掛號提醒。 |

### 回應欄位

所有回傳掛號提醒的端點（GET、POST、PUT、depart、attend、cancel）都新增兩個欄位，形狀與出發／到診一致：

| 欄位 | 型別 | nullable | 說明 |
|---|---|---|---|
| `cancelled_at` | string（ISO 8601，帶 offset） | 是 | null＝沒有取消 |
| `cancelled_by_user_id` | string | 是 | 與 `cancelled_at` 同時有值／同時為 null |

## 需求二：清單依「即將到來／過去」分開查，過去的要分頁

### 「過去」的定義只能有一個，而且放在後端

前端畫面分兩區：「即將到來」與「過去的門診」。產品規則是：

- **即將到來**：沒有取消、而且當日還沒結束的門診
- **過去**：當日已結束，**或已經取消**的門診（一筆下個月的門診取消了，也歸在過去）

「當日結束」沿用報告 §7 的定義（當地午夜，但不早於門診後 60 分鐘），與標記 `missed` 同一條界線。

這條界線同時決定兩件事：列表怎麼分、「刪除全部歷史紀錄」刪哪些（需求三）。**兩者必須用同一份判定**，否則會發生「畫面上過去的門診顯示 23 筆，按下刪除全部卻刪了 25 筆」。

### `GET /api/appointments/reminders` 新增 `scope` 參數

| 參數 | 說明 |
|---|---|
| `target_user_id` | 選填，同現有 |
| `scope` | `upcoming` 或 `past`。**帶了 `scope` 才用新的回應格式**（見下方相容性） |
| `limit` | 只對 `scope=past` 有效，預設 20、上限 50 |
| `cursor` | 只對 `scope=past` 有效，上一頁回應的 `next_cursor` |

- `scope=upcoming`：依 `appointment_at` **由早到晚**，**不分頁**（未來的門診量本來就少），回全部
- `scope=past`：依 `appointment_at` **由新到舊**，cursor 分頁

**回應（帶 `scope` 時）**：

```json
{
  "items": [ /* 與現有單筆形狀相同的掛號提醒 */ ],
  "next_cursor": "opaque-string-or-null",
  "total_count": 23
}
```

- `next_cursor`：null 代表沒有下一頁。`scope=upcoming` 一律 null
- `total_count`：該 scope 的總筆數，不是這一頁的筆數。前端要用它顯示「過去的門診（23）」與確認框裡的「刪除全部 23 筆」

**不設「只回最近 12 個月」之類的預設上限。** 紀錄是永久保留的，「載入更多」必須能一路翻到最舊的一筆；效能交給分頁處理。

### 相容性：不帶 `scope` 時維持現有行為

目前部署中的前端打的是 `GET /reminders?include_past=true`，回傳陣列。**不帶 `scope` 時請完全維持現有行為**（陣列、`include_past` 語意不變），前端切換到新參數之後，舊的那條路才可以擇期拿掉。

## 需求三：一次刪除全部歷史紀錄

### `DELETE /api/appointments/reminders?target_user_id=&scope=past`

- **只刪 `scope=past` 的那些**，定義與需求二完全相同（當日已結束或已取消）。**即將到來的一筆都不能動**——這是這個端點能存在的前提
- **只有本人可以按**（已拍板），家屬一律 403，細節見需求五「刪除全部歷史紀錄：只有本人」
- 回應：`{ "deleted": 23 }`，實際刪除的筆數。前端顯示「已刪除 23 筆」
- 沒有任何過去紀錄時回 `{ "deleted": 0 }`，不是 404
- 不帶 `scope`、或 `scope` 不是 `past` 時回 400——**不能因為漏帶參數而刪掉全部掛號**

### 為什麼要後端一次刪，不讓前端逐筆呼叫 `DELETE`

- 分頁之後，前端手上只有已經載入的那幾頁，逐筆刪會刪不乾淨
- 幾十次請求中途失敗會留下刪一半的狀態，長輩看到的是「按了刪除全部，還剩一半」
- 請盡量在同一個操作裡完成（例如單一 `delete_many`）

## 需求四（前次追加，目前未實作）：同一時間一律不能有兩筆

2026-09-10 追加過一條規則：**同一位就診者，同一個 `appointment_at`（同一瞬間）只能有一筆未取消的掛號，不論醫院或科別是否相同。** POST 與改了 `appointment_at` 的 PUT 撞到時回 409。

現有的 `AppointmentService._ensure_not_duplicate` 只擋「同時間、同醫院、同科別」，註解明寫「同一時間但不同醫院或不同科別**不擋**」。請改成只要同一瞬間、未取消就擋。

前端已經先擋，這條是清單過期時（例如家人剛在另一支手機建了同一時間的掛號）的最後一道防線。

注意與需求一的交互：**已取消的不算撞時段**。取消了 9/15 09:30 那一筆，再建一筆 9/15 09:30 應該要能建。

## 需求五：授權與邊界條件

2026-09-12 前端讀過後端現有的掛號程式碼（`app/routers/users/appointments.py`、`appointment_service.py`、`appointment_repository.py`、`family_authorization_service.py`、LINE webhook）後補充。分三部分：已確認沒問題的、新端點必須做到的、既有程式碼要修的洞。

### 已確認沒問題的（新端點請沿用）

- 身分只來自 JWT（`get_current_user`），body 帶的任何 `user_id` 都不構成授權依據。
- LINE 按鈕的操作者來自已驗 `X-Line-Signature` 的 webhook 事件。
- 授權查的是**就診者**的族譜，不在族譜裡的人兩種模式都會被拒絕。對象是 `reminder.user_id`，不是 `creator_user_id`——建立者後來被移出家庭或被降級，就不能再動那筆。
- 出發／到診是「以來源狀態為條件」的原子更新，兩個人同時按只有一邊寫入。

### 新端點（cancel、刪除全部）必須做到的

1. **操作者只取自 token。** `cancelled_by_user_id` 由 JWT 決定；request body 與 query 一律不能影響它。
2. **授權對象：**
   - cancel：先讀出 `reminder.user_id`，對它授權（與 depart／attend 相同）。
   - 刪除全部：只有本人（已拍板）。`target_user_id` 省略或等於操作者本人才放行；帶了別人的 id 回 403，**不能退回去刪操作者自己的紀錄**。`delete_many` 的 filter 用操作者本人的 user_id。
3. **cancel 的授權用 `has_legacy_equivalent=False`**，與下方「所有掛號寫入路徑改成嚴格判定」一致。刪除全部不經過家庭授權，只比對是不是本人。
4. **cancel 用條件式原子更新**，一次寫入，不先讀後寫：
   - 條件：`status ∈ {scheduled, departed}` **且 `day_end_at > now`**
   - 沒命中時重讀：已是 `cancelled` → 200 冪等；`attended` → 409；`missed` 或當日已結束 → 409；不存在 → 404
   - `day_end_at > now` 不能省：當日結束後到排程器標記 `missed` 之前有一段空窗，這時狀態還是 `scheduled`，只看狀態會讓人取消一個已經結束的門診。
5. **cancel 與其他動作同時發生：**
   - 與 attend 同時：兩者都是對同一組來源狀態的條件更新，只會有一邊成功，另一邊走「重讀 → 冪等或 409」。
   - 與 PUT 改時間同時：見下方「洞 1」。
   - 排程器已經搶下、正在送的那一則推播，取消後仍會送達；卡片上的按鈕會回「已取消」。可以接受，請在報告裡註明。
6. **刪除全部的判定與列表同一份**：`{user_id, $or: [{day_end_at: {$lte: now}}, {status: "cancelled"}]}`，整個操作用同一個 `now`。「即將到來」與「過去」必須互斥、合起來涵蓋全部——請寫一條測試釘住這件事。
7. **404 先於 403**：沿用現有順序即可（外人只能分辨某個 id 存不存在，看不到內容，id 也不好猜）。

### 既有程式碼要修的洞

**洞 1：改門診時間會洗掉剛寫入的「已到診」**

`AppointmentService.update` 先 `get` 讀出現況、檢查 `current.status == "attended"`，再用無條件的 `update_fields`（`$set`）寫入。如果讀完之後、寫入之前，另一個人（家屬，或本人按了 LINE 卡片）剛好回報到診，這次 PUT 會套用 `_RESET_ON_RESCHEDULE`：狀態改回 `scheduled`、清空 `attended_at`／`attended_by_user_id`、三個推播重新排定。**到診紀錄消失，家屬還會再收到提醒。**

需求一新增的「已取消不能改時間」如果照同樣方式實作，也會有一樣的洞：取消後的瞬間被 PUT 復活。

請把改時間的寫入改成條件式：`{_id, status ∈ {scheduled, departed, missed}}`（排除 `attended` 與 `cancelled`），沒命中就重讀、回 409。

**洞 2：當日結束後到標記 missed 前，仍然可以回報到診**

`mark_departed`／`mark_attended` 的條件只看 `status`。當日結束之後、排程器下一次 `mark_missed` 之前，狀態還是 `scheduled`／`departed`，這段時間按「我已到診」會成功——隔天凌晨按一下，一個沒去的門診就變成已到診。產品已拍板不做補登到診，這個空窗等於留了一個補登的後門。

請在兩者的條件加上 `day_end_at > now`，沒命中且當日已結束時回現有的 `missed` 409。

### 所有掛號寫入路徑改成嚴格判定（已拍板）

系統目前預設是影子模式（`DEFAULT_MIGRATION_STATE = "shadow"`），影子模式下的判定是「在族譜裡就放行」。現有的掛號端點全部用預設的 `has_legacy_equivalent=True`，所以只有讀取權的 MEMBER 目前可以新增、修改、刪除長輩的掛號，也能代按出發／到診。

**已拍板：只有讀取權的家人不能更動掛號，影子模式下也一樣。** 依 `authorize` 自己的註解，導入 RBAC 之後才出現的路徑本來就該用 `False`；掛號整個功能都是新的，沒有要保留的既有行為。

| 路徑 | 目前 | 改成 |
|---|---|---|
| `POST /reminders`（為別人建立） | `_authorize(..., "WRITE")`，預設 True | `has_legacy_equivalent=False` |
| `PUT /reminders/{id}` | 同上 | 同上 |
| `DELETE /reminders/{id}` | 同上 | 同上 |
| `POST .../depart`、`.../attend`（含 LINE 卡片按鈕，兩者都走 `_authorize_report`） | 預設 True | 同上 |
| `POST .../cancel`（新） | — | 同上 |
| `GET /reminders`（讀取） | 預設 True | **不動**：MEMBER 本來就有 GENERAL 讀取權 |

本人（操作者＝就診者）不受影響，一律是 OWNER。

**連帶一：家屬推播的收件人要跟著收緊。** 目前影子模式下，家屬推播（T-1h、T+0、T+30）送給族譜全員，包括 MEMBER。寫入改成嚴格之後，MEMBER 收到的卡片上「我已出發」「我已到診」按下去必定 403——這正是 `NOTIFICATION_POLICY` 註解裡要避免的「送他一張按下去必定 403 的卡片」。請讓 `appointment_reminder` 的收件人在兩種模式下都是 GUARDIAN 與 CAREGIVER（強制模式本來就是），不再在影子模式下擴及全員。

**連帶二：前端需要一份嚴格判定的權限。** 前端依族譜回應裡的 `my_permissions` 決定要不要顯示新增、編輯、取消、刪除、出發／到診的按鈕，而 `my_permissions` 是套用過遷移狀態的值——影子模式下 MEMBER 的 `my_permissions` 仍會回報 GENERAL WRITE，前端就會顯示按下去必定 403 的按鈕。

請在族譜成員的回應裡另外提供一份**不受遷移狀態影響、純 RBAC（含委任）**的權限，形狀與 `my_permissions` 相同，例如 `my_strict_permissions`（名稱可調整，請回報）。前端改用它判斷掛號的寫入能力。這份值要由後端的 `can()` 算出來，不要讓前端用 `my_role` 自己推算——委任會讓一位 MEMBER 暫時具備 GUARDIAN 的資料權限，而 `my_role` 看不出來。

**上線順序**：後端的嚴格判定與這個新欄位要一起上線。只上嚴格判定、前端還沒改用新欄位的那段期間，MEMBER 會看到按了必定 403 的按鈕。

**測試**：影子模式下 MEMBER 對掛號的每一條寫入路徑（含 LINE 卡片按鈕）都是 403，GUARDIAN／CAREGIVER 照常；影子模式下 MEMBER 收不到家屬推播；嚴格權限欄位在影子模式下對 MEMBER 回報沒有 GENERAL WRITE，對受委任者回報有。

### 刪除全部歷史紀錄：只有本人（已拍板）

一次刪光所有就醫紀錄是不可逆的批次操作，**只有就診者本人可以按**。家屬一律不行，GUARDIAN、CAREGIVER、受委任者都一樣。

- 判定只看操作者是不是本人，不經過家庭授權
- 省略 `target_user_id`＝本人
- **帶了別人的 `target_user_id` → 403，不能退回去刪操作者自己的紀錄。** 如果家屬帶著長輩的 id 呼叫，後端「忽略參數、改刪自己的」，家屬會在不知情的情況下刪光自己的就醫紀錄
- 403 detail 建議：「只有本人可以刪除全部歷史紀錄。」

單筆刪除維持現狀：有寫入權的家屬可以代刪，套用上面的嚴格判定。

## 不做

- 取消時發任何推播（已拍板）
- 補登到診、放寬 `attend` 的時間限制（已拍板）
- 任何保留期或自動刪除排程（已拍板永久保留）
- 「刪除全部」擴及即將到來的門診
