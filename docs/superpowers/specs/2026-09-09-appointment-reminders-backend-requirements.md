# 掛號提醒後端需求（給 CARE 後端）

日期：2026-09-09（2026-09-10 修訂：提醒節奏與建立流程）
狀態：待後端評估
提出方：LIFF 前端

## 這份文件是什麼

LIFF 前端要新增「掛號提醒」功能，與現有的用藥提醒同構：同一套家庭權限、同一套 LINE 推播、同樣可以幫家人設定。前端可以照著用藥提醒的形狀把整層 UI 寫出來，但**後端目前沒有任何對應的資料模型與端點**。

以下是前端據以實作的契約提案。欄位命名與路徑都可以調整，但請回報最終形狀——前端會照著寫型別。文末列了需要後端拍板的問題。

## 與用藥提醒的關鍵差異

| | 用藥提醒 | 掛號提醒 |
|---|---|---|
| 性質 | 週期性（每天固定時段） | **單次事件**（某年某月某日某時某分） |
| 時間欄位 | `slot_type` + `scheduled_time` + 起訖日 | 一個絕對時間點 `appointment_at` |
| 錯過的代價 | 今天漏一次，明天還有 | **錯過就是錯過**，要重新掛號 |
| 完成狀態 | 每日打卡 log | 單次的「已出發 → 已到診」 |

第三列直接決定了時區處理的優先級（見時區章節），第四列決定了狀態機的設計。

不能硬套 `MedicationSlotType`——掛號沒有早中晚睡前的概念。

## 資料模型（提案）

```
AppointmentReminder
  id                  str
  user_id             str    就診者的 LINE userId
  creator_user_id     str    建立者（可能是家屬）
  appointment_at      datetime (timezone-aware)  門診時間，精確到分鐘

  facility_id         str | None   院所查詢回傳的 id，可能為 null（見下方說明）
  hospital_name       str          權威顯示值
  hospital_address    str | None
  hospital_phone      str | None
  department          str          科別
  doctor_name         str | None
  serial_number       str | None   看診號
  note                str | None   自由備註

  status              scheduled / departed / attended / missed / cancelled
  departed_at         datetime | None
  departed_by_user_id str | None   實際按下「我已出發」的人（本人或代按的家屬）
  attended_at         datetime | None
  attended_by_user_id str | None   實際按下「我已到診」的人
  enabled             bool
  created_at          datetime
  updated_at          datetime
```

**`facility_id` 不能當外鍵。** 現有的 `MedicalFacility.id` 型別是 `str | None`，也就是後端自己也承認查詢結果不一定帶 id。所以院所名稱是權威顯示值，`facility_id` 只是「有就存著，日後想回連時用得上」。整條流程不可以在 `facility_id` 為 null 時失敗。

**刻意不放的欄位：病名、主訴、診斷。** 與用藥提醒的 `indication` 同一條安全邊界——那類資訊只該在 LIFF 內給有權限的人看，不該有機會流進推播訊息。這裡連存都不存，就不會有人不小心把它塞進 Flex 卡片。

`department`（科別）比較微妙，見「推播文案的隱私邊界」。

## 提醒節奏與狀態機

**已拍板：不做前一天的提醒，也不做當天早上的提醒。** 使用者不能自訂提前多久提醒——這個節奏由後端固定。

| 時機 | 對象 | 動作 |
|---|---|---|
| `T-1h` | 本人 **＋家屬** | 推播 Flex 卡片，按鈕「我已出發」 |
| `T+0`（門診時間），若已按過「我已出發」 | 本人 **＋家屬** | 推播 Flex 卡片，按鈕「我已到診」 |
| `T+0`，若**沒**按過「我已出發」 | 本人 **＋家屬** | 推播催促（時間到了，還沒出發） |
| `T+30min`，`status` 仍不是 `attended` | 家屬 | 家屬警報 |
| 當日結束仍不是 `attended` | — | 標記 `missed`，停止所有推播 |

狀態轉移：`scheduled` →（按我已出發）→ `departed` →（按我已到診）→ `attended`。

按下「我已到診」→ 寫入 `attended_at`、**取消後續所有排程**（包含 T+30 的家屬警報，以及尚未發出的本人與家屬推播）。

### 誰收到推播、誰能按

**已拍板：家屬與本人收到同一組推播（T-1h、T+0），卡片上的按鈕也相同，任一方按下即生效。**

家屬帶長輩去看診時，人在現場的是家屬，而長輩不一定會操作手機。所以「我已出發」「我已到診」兩顆按鈕家屬按得下去，按下之後就消掉**雙方**的後續排程——不會發生家屬按了、長輩手機還在響的情況。實際按下的人記在 `departed_by_user_id` / `attended_by_user_id`。

「家屬」的定義：**與家屬警報同一個 resolver**，見下一節。三則推播與一則警報的收件人是同一群人，不要有兩套名單。

一個要注意的副作用：這等於每次門診會對每一位符合條件的家庭成員發出最多三則推播。人多的家庭推播量會明顯上升，若後端有推播配額或節流機制，請在這裡先評估。

**注意 T+30 的判定是「不是 `attended`」，不是「不是 `departed`」。** 已經按了「我已出發」但半小時後還沒到診，家屬**仍然要收到通知**——這種情況（出發了卻沒到）比從頭沒動作更值得家人關心，可能是路上出了狀況。

### 沿用既有引擎

用藥提醒已經有「T+0 提醒 → T+20 催促 → T+30 家屬警報」的雙階遞進排程引擎。上面的節奏是同一個骨架，只是階段換成 T-1h / T+0 / T+30，且中間多一個 `departed` 中繼狀態。請沿用，不要新寫一套。

### 家屬的收件人名單

**請沿用用藥提醒現有的 resolver，不要新寫一份。** 兩個功能對「誰算家屬」的答案必須一致——如果掛號用一套邏輯、用藥用另一套，同一個家庭會出現「用藥沒吃會通知我、掛號沒去不會」這種無法解釋的行為，而且日後改權限規則一定會漏改一邊。

### `notify_at` 請由後端算好隨 GET 回傳

用藥提醒的 `DEFAULT_SLOT_TIMES` 目前是前後端各存一份，前端型別檔上就註明著「兩份必須一致，這裡改了而後端沒改，編輯視窗會判定使用者自訂過時間而不再跟隨」。那個坑不要再挖第二次。

`GET /reminders` 的每一筆回應請直接附上後端算好的觸發時間點：

```json
"notify_at": ["2026-09-15T08:30:00+08:00", "2026-09-15T09:30:00+08:00", "2026-09-15T10:00:00+08:00"]
```

前端只負責原樣顯示「我們會在這些時間提醒你」，零計算、零常數、零漂移。

## 建立流程：院所從既有的查詢工具帶入

**這一節主要是前端的事，但有兩個後端相依，寫在這裡讓你們一起評估。**

使用者不手打醫院名稱。新增掛號提醒的流程是：

1. **選院所**——沿用首頁「找附近醫院」那一套。既有的 `GET /api/medical/facilities?keyword=`（關鍵字）與 `GET /api/medical/nearby`（附近）都回傳完整的 `MedicalFacility`，前端直接複用，不需要新端點。
2. **選科別**——從該院所回傳的 `departments[]` 挑，不用手打。醫學中心會有三十幾個科，用既有的摺疊 chips 呈現。
3. **選日期**。
4. **選時間**——顯示該院所 `clinic_time[該weekday].slots`（例如「上午 08:30–12:00、下午 14:00–17:00」）當作參考，**下方另有分鐘級的自訂輸入**，使用者可以填 `09:47` 這種不落在任何 slot 裡的時間。

### `clinic_time` 只能拿來提示，不能拿來限制

這點很重要，請不要在後端加驗證擋掉它。

`clinic_time` 是**整間院所的營業時段**，不是各科的門診表。台大醫院的心臟內科可能只有週二上午王醫師的診，但 `clinic_time` 會顯示週一到週五 08:00–17:00。反過來也有：使用者手上那張掛號單寫的時間，可能就是不在我們資料裡的時段。

**權威是使用者手上的掛號單，不是我們的資料庫。** 所以：

- 落在 slots 內 → 正常送出
- 落在 slots 外 → 前端顯示一行提示（「這個時間不在我們查到的門診時段內，請再確認一次」），但**允許送出**
- 該日 `isClosed` 或整個 `clinic_time` 是 null → 不提示，直接讓使用者填

`business_status` 本來就有 `call_ahead`（請電洽）與 `unknown`（無資料）兩個狀態，等於後端自己已經承認這份資料不完整。建立流程要跟這個承認一致。

### 兩個後端相依

**(a) 編輯時要能重查單一院所。** 使用者建立提醒後想改日期，畫面要重新顯示那天的 `clinic_time`，但手上只有存下來的 `facility_id` 與 `hospital_name`。目前沒有「依 id 查單筆院所」的端點，只能拿名稱去打 keyword 搜尋——名稱重複的連鎖診所會查錯家。

→ 希望補一支 `GET /api/medical/facilities/{id}`。若不做，前端會退回 keyword 搜尋並在名稱不唯一時要求使用者重選，請告知採哪條。

**(b) `facility_id` 為 null 時要能正常建立。** 見資料模型那節。

## API

| 方法 | 路徑 | 用途 |
|---|---|---|
| `GET` | `/api/appointments/reminders?target_user_id=` | 查某人的掛號提醒。省略參數＝本人 |
| `POST` | `/api/appointments/reminders` | 建立 |
| `PUT` | `/api/appointments/reminders/{id}` | 修改 |
| `DELETE` | `/api/appointments/reminders/{id}` | 刪除 |
| `POST` | `/api/appointments/reminders/{id}/depart` | 標記已出發 |
| `POST` | `/api/appointments/reminders/{id}/attend` | 標記已到診 |

後兩支主要由 Flex 卡片的按鈕打，LIFF 頁面上也會有對應按鈕（使用者可能滑掉了那則訊息）。兩支分開而不是一支帶 `action` 參數：Flex 按鈕的 postback 直接對應一個端點最單純，狀態轉移的合法性也各自檢查得清楚。

`GET` 建議支援 `include_past=false` 預設值：列表頁預設只顯示未來的診，過去的另外收起來。若後端不做，前端自己濾也可以，請告知。

### `POST` body

```json
{
  "user_id": "U...",
  "appointment_at": "2026-09-15T09:30:00+08:00",
  "facility_id": "abc123",
  "hospital_name": "台大醫院",
  "hospital_address": "臺北市中正區中山南路7號",
  "hospital_phone": "0223123456",
  "department": "心臟內科",
  "doctor_name": "王大明",
  "serial_number": "23",
  "note": null
}
```

### `PUT` 請用 `exclude_unset`，不要用 `exclude_none`

**這是本文件最重要的一條實作要求。**

用藥提醒的 `update_reminder` 用了 `model_dump(exclude_none=True)`，repository 又再濾一次 `None`，結果是 `end_date: null` 永遠送不進去——使用者一旦設過結束日期就再也改不回「長期」，只能改成別的日期。前端目前得在編輯視窗裡擋下這個操作並就地解釋為什麼不行。

掛號提醒有五個 nullable 欄位（`doctor_name`、`serial_number`、`note`、`hospital_phone`、`hospital_address`），使用者一定會遇到「填錯醫師名字想清空」。用 `exclude_unset` 的話，「沒帶這個 key」＝不動、「帶了但是 null」＝清空，兩者語意分得開，前端也才有辦法用型別把誤用擋在編譯期。

## 權限

沿用既有的家庭 RBAC，掛號資訊歸類為 **GENERAL** 級（與用藥同級，不是 sensitive）：

- 讀某人的掛號提醒：對他有 `GENERAL READ`
- 幫某人建立／修改／刪除：對他有 `GENERAL WRITE`
- `POST` 的 `user_id` 必須是自己或家庭成員——請沿用用藥提醒現有的檢查（前端會顯示後端回的中文 `detail`，掛號請給對應的文案）

前端會用既有的 `canWriteGeneral` 決定要不要渲染「新增」按鈕，但那只是「不要給使用者一個按下去必定 403 的按鈕」，**真正的授權邊界永遠是後端的 403**。前端不重算權限矩陣。

### `depart` / `attend` 的權限（已拍板）

這兩支**本人一定可以打，對就診者有 `GENERAL WRITE` 的家屬也可以代打**。理由見「誰收到推播、誰能按」。

實際按下的人寫入 `departed_by_user_id` / `attended_by_user_id`——出了爭議時要查得出是誰說「他到了」。

狀態轉移的合法性請在後端檢查：`attend` 可以從 `scheduled` 或 `departed` 打（使用者可能沒按出發就直接到了），但 `depart` 不能從 `attended` 往回打，已經是 `cancelled` / `missed` 的也不接受。

## 時區：這次請務必處理

用藥提醒目前全程以 UTC 判定觸發時間，所以設定「早上 08:00」實際在台灣時間 16:00 推播。前端刻意不做補償，等後端修。

同樣的問題搬到掛號提醒會**致命**：用藥每天都有，晚 8 小時只是煩人；掛號 9/15 09:30 的診如果在 17:30 才提醒，那個診就是錯過了，而且錯過的是一個要等好幾週才排得到的門診。

而且這次的提醒節奏全部相對於 `appointment_at`（T-1h / T+0 / T+30），時區一錯，三則推播會整組錯開，家屬警報也會在半夜發出去。

**要求：**

- `appointment_at` 存成 timezone-aware timestamp
- API 收發一律 ISO 8601 帶 offset（`2026-09-15T09:30:00+08:00`）
- 排程判定用使用者的當地時間，不是 UTC
- 前端不做任何時區換算，原樣送、原樣顯示

## 推播文案的隱私邊界

用藥提醒有一條既定原則：適應症只在 LIFF 內給有權限的人看，**保證不會出現在推播訊息中**。

掛號提醒對應的敏感欄位是 `department`（科別）。「王媽媽今天 09:30 在台大醫院精神科有診」這則訊息會出現在家屬的 LINE 聊天室裡，而 LINE 訊息可能被同一支手機的其他人看到。

這件事因為「家屬也收 T-1h 提醒」的決定而變得更要緊：家屬原本只在出事時（T+30 警報）才收到訊息，那是罕見事件；現在**每一次門診都會發三則給家屬**，科別若進文案，等於每次看診都對全家廣播一次科別。

**建議定案：推播文案只含日期時間與醫院名稱，科別、醫師、看診號一律只在 LIFF 內顯示。** 家屬點進 LIFF 就看得到完整資訊（他本來就有 `GENERAL READ`），差別只在於這些字不會躺在聊天室的訊息列表裡。若產品端要改，請在動工前提出。

## 不做

- 串接任何醫院的掛號系統（使用者自己輸入掛號資訊；我們只做提醒，不做代預約）
- **使用者自訂「提前多久提醒」**——提醒節奏（T-1h / T+0 / T+30）由後端固定。這條講的是提醒的時機，不是門診時間；門診時間當然由使用者輸入，而且精確到分鐘（見「建立流程」）
- 用 `clinic_time` 驗證或擋下使用者填的門診時間（見「只能拿來提示，不能拿來限制」）
- 交通時間估算、導航（既有的院所卡片已經有 Google Maps 導航連結，重複做沒意義）
- 掛號提醒與用藥提醒的資料互通

## 已拍板的產品決策（不需要再問，照做即可）

- 提醒節奏固定為 T-1h / T+0 / T+30，使用者不能自訂
- 家屬與本人收到同一組推播（T-1h、T+0），按鈕相同
- 家屬可以代按「我已出發」「我已到診」
- T+30 的判定是「不是 `attended`」，不是「不是 `departed`」
- 推播文案不含科別、醫師、看診號
